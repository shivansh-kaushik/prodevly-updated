This part of the plan covers the admin panel at /admin and the backend shared with the public site. It reuses the backend patterns that worked in the tour-travel-3d CRM and fixes the gaps its audit found. Every number in the panel comes from records the team enters. The panel never shows sample figures.
Next.js 16.4 App Router TypeScript strict Tailwind 4 MongoDB + Mongoose 9.11 zod 4 jose 6 + bcryptjs 3 recharts 3 Node 22 LTS
Versions are re-checked against npm view and node_modules at install time. Mongoose 9 needs Node 20.19 or later, so the project pins Node 22 LTS in .nvmrc and engines.
1. Roles and permissions
There are two access roles. superadmin is held by Aman Gupta, Lakshya Sharma and Shivansh Kaushik at launch and can see and change everything. admin is every other team member. Job titles such as Frontend developer or Project manager live in a separate job-role field and grant no access.
Code checks capabilities and never role names. ROLE_DEFAULTS maps each role to a set of capabilities. An admin's effective capabilities are the role defaults plus any grants a superadmin has switched on for that person. The sidebar, buttons and money columns hide when a capability is missing, and every page, route handler and service checks the capability again on the server.
Key for the table. SA means superadmins. A means every admin by default. G means an admin only after a superadmin grants it. Own means records the admin created or is assigned to.

Hard rules
Only superadmins manage admins. That covers create, change role, change grants, reset password, remove and reactivate. admin:manage cannot be granted.
No one can remove, deactivate or demote their own account. The API answers SELF_ACTION (403).
The system refuses any change that would leave zero active superadmins and answers LAST_SUPERADMIN (409). The count and the write run in one transaction, and the transaction also increments the guard document counters/superadmin-guard. Two superadmins acting at the same moment therefore conflict, one transaction retries, and the retry fails the check.
Delete means deactivate. Removing an admin sets status: 'deactivated', stores who removed them, when and why, and increments tokenVersion, which ends every session on the next request. The account, its work logs, payouts and audit entries stay. The remove dialog lists the person's open tasks so they can be reassigned in the same step. The email stays reserved. To bring the person back a superadmin reactivates the account and the person must set a new password.
A superadmin can demote or remove another superadmin, subject to rules 2 and 3. Creating a superadmin, demoting or removing one, changing grants, resetting a password, editing pay profiles and exporting data all need step-up. The superadmin re-enters their own password and the step-up stays valid for 10 minutes.
Per-admin grants are optional and decided by superadmins on the admin's page. Capabilities are read from the database on every request, so a change applies on the next click. Each change is written to the audit log with the before and after sets.
Admins cannot change their own role, grants or pay profile.
Business records are archived. Money entries are voided with a reason and are never deleted. Permanent delete exists only for clients, tasks, enquiries and media with nothing linked to them, and only for superadmins.

3. Data model
Conventions
One Mongoose 9 model per collection, typed through declare module 'mongoose' { interface Models { ... } } and exported as models.X ?? model('X', schema). Every model is registered in src/models/index.ts so populate() and the index script see all of them.
Every document has createdAt and updatedAt from timestamps, plus createdBy and updatedBy stored as an actor snapshot { id, name }. History and audit views render without joins and keep the name after an account is removed.
Archivable documents carry archivedAt and archivedBy. Default queries exclude archived records.
Human references come from Counter.nextSequence(key), for example CL-0007, PRJ-0042, PRJ-0042-T007 and PAY-FY27-0001. Money references use a financial-year counter that starts again each April.
Date-only business fields such as received date, due date and work date are stored as UTC midnight of the calendar date and are never shifted by time zone. Timestamps are real instants and are bucketed in Asia/Kolkata.
Links are derived on the server. When an entry names a task, the service reads the task and sets projectId and clientId from it. When it names a project, the service sets clientId. A request whose ids disagree is rejected with LINK_MISMATCH. A task cannot move to another project, and a project cannot move to another client, once a work log or money entry references it.
Every money entry embeds the shared Money subschema as amount.
The Money subschema
amountMinor integer in the currency's minor unit, greater than 0
currency ISO 4217 code, uppercase, from the enabled list in Settings
fxRate INR per 1 unit of the currency, up to 6 decimals, exactly 1 for INR
fxDate the date the rate applies to
fxSource 'identity' | 'table' | 'bank' | 'manual'
inrMinor integer paise, computed on the server and never sent by the client

Flow
Company-paid expenses are recorded directly as paid by a superadmin or an admin with expense:record.
Out-of-pocket expenses start as submitted by the admin. A superadmin approves them, which means we owe the admin, and later marks them paid with the reimbursement date. Reimbursements are never recorded as team payouts, so nothing is counted twice.

4. Money
Currency codes are ISO 4217 three-letter codes in uppercase. src/config/currencies.ts lists each code with its minor-unit digits, for example INR 2, USD 2, EUR 2, GBP 2, AED 2, JPY 0 and KWD 3. Superadmins choose the enabled set in Settings. INR is the base currency and cannot be disabled.
Amounts are stored as integers in minor units. A user types 1,250.50 and the form sends 125050. Amounts are never stored as floats.
Each entry captures the rate for its own date. On create, the service looks up the latest fxRates row for that currency on or before the entry date. If that row is older than fxStaleDays, the form asks for a rate and the API answers FX_RATE_MISSING until one is given. The user can override the rate with the one the bank applied, or type the INR amount that arrived and let the service derive the rate (fxSource: 'bank'). INR entries use rate 1.
The INR value is computed once on the server as inrMinor = round(amountMinor × fxRate × 10^(2 − digits(currency))). For example, USD 1,000.00 at 83.42 is stored as 8,342,000 paise, which is INR 83,420.00.
Saved entries do not change when the FX table changes. Editing the amount, currency or date recomputes rate and INR unless the rate came from the bank or was typed by hand. Every edit is in the audit log.
Third-party and team payouts recorded as due capture the rate again on the day they are marked paid, because that is when INR left the account.
Dashboards sum amount.inrMinor and nothing else. Native amounts appear only grouped by currency as a secondary line, for example "USD 4,000.00 (INR 3,33,680.00)". INR uses en-IN grouping.
Voided entries and rejected expenses are excluded from every total and stay visible with a Void or Rejected tag. Refunds to clients are client payments of type refund and are subtracted from received.
Period filters use the settlement date, which is receivedOn, paidOn or spentOn. Open items use dueOn. The financial year runs from 1 April to 31 March.
There is no payment gateway. Entries record money that moved by bank transfer, UPI, PayPal, Wise, cash and similar modes.
Which statuses count
Collection | Counted as settled | Counted as open | Date used | 
clientPayments | received, with refunds subtracted | Outstanding is computed from contracts and milestones | receivedOn | 
thirdPartyPayouts | paid | due plus open work-order balances | paidOn, or dueOn when open | 
expenses | approved and paid, because the money is already spent | approved with paidFrom: 'admin' is a reimbursement we owe | spentOn | 
teamPayouts | paid | due | paidOn, or dueOn when open | 
Outstanding from clients
Billable total per project is the contract amount for fixed and milestone projects. For hourly and retainer projects it is the sum of milestones marked invoiced or paid, so the team adds one milestone per invoice.
Received toward the contract is the sum of contractEquivalentMinor over received payments, minus refunds.
Outstanding equals billable total minus received toward the contract, in the contract currency. The Overview converts each project's outstanding to INR at the latest table rate and labels the tile "at latest rates".
A new payment in the contract currency that would push received above the billable total is refused with PAYMENT_EXCEEDS_DUE, unless a superadmin ticks "Record as advance". Payments in another currency show a warning and are not blocked.
Project margin in INR
Received is the sum of inrMinor over received client payments for the project, minus refunds.
Third-party cost is the sum over paid third-party payouts for the project.
Expense cost is the sum over approved and paid expenses charged to the project.
Team cost is the sum of allocations.inrMinor over paid team payouts where allocations.projectId is the project.
Margin is Received minus Third-party cost minus Expense cost minus Team cost. Margin percent is Margin divided by Received and is shown only when Received is above zero.
Projected margin is the billable total in INR at the latest rate minus committed costs. Committed costs add due payouts, open work-order balances (agreed minus paid minus due, at the latest rate) and due team allocations to the settled costs.
Team cost allocation
When a superadmin records a team payout, the form proposes allocations in proportion to the person's logged minutes per project in the payout period. The superadmin can edit the split. Allocations cannot exceed the payout amount and the remainder is company overhead. Company totals use the payout amount, and project margins use the allocations, so nothing is counted twice.
Internal and company figures
Projects under "ProDevly (internal)" never count as revenue. Their costs count in company totals and show as an Internal row in project tables.
Company net for a period is external received minus paid third-party payouts minus approved and paid expenses (company and project scope) minus paid team payouts.
Money dashboards share one pipeline builder, ledgerUnionPipeline() in src/services/dashboards/ledger.ts. It starts from clientPayments and uses $unionWith to bring in the other three money collections, each projected to { kind, status, date, clientId, projectId, taskId, inrMinor }. Team payouts are unwound by allocation for project views and kept whole for company views. A single $facet then produces every tile and chart for the screen.

6. Work tracking for admins
Assignments
A task has any number of assignees. Each one is an admin or a third party, stored as { kind, id, name }.
Assigning or unassigning writes an audit entry with the task, project and client in context.
My work shows tasks newly assigned since the person's last visit with a count badge in the sidebar. There are no email notifications in the first release.
Removing an admin lists their open tasks for reassignment in the same dialog.
Work logs
Logged from the task page or the quick-log form on My work with date, duration in hours and minutes, a note and a billable flag.
Each entry is 5 to 720 minutes. A person's total for one day cannot pass 16 hours, and the form warns above 12 hours.
Logs cannot be added to cancelled tasks or archived projects.
Admins can edit or delete their own logs for workLogEditWindowDays (7). After that only a superadmin can change them. A log covered by a paid team payout is locked for everyone, and the API answers ENTRY_LOCKED.
Status history
Every task and project status change pushes { from, to, at, by, note } onto statusHistory.
Cycle time is measured from the first move to in_progress to done. On-time means completedAt is on or before dueOn.
Reopening a done or cancelled task needs a note.
Payouts to admins
A superadmin records a team payout for a person and a period. The form proposes an amount from the pay profile. Monthly uses the rate. Hourly uses logged minutes in the period times the rate. Per task uses tasks the person completed in the period times the rate.
The proposal is stored as suggestion next to the final amount, so differences stay visible.
Allocations to projects are proposed from logged minutes per project and can be edited.
Marking a payout paid locks the work logs in its period and captures the FX rate for the paid date.

7. Auth and security
Sessions
A jose HS256 JWT signed with AUTH_SECRET, issuer prodevly, audience prodevly-admin, with claims sub, role, tv (token version), iat, exp and auth_time.
The cookie is __Host-pdv_session in production and pdv_session on localhost. It is httpOnly, Secure in production, SameSite Lax, Path / and has no Domain.
Sessions last 8 hours and slide. The cookie is reissued when less than half the time is left, with a hard limit of 12 hours after auth_time.
tokenVersion increments on password change, password reset, role change, deactivation and "Sign out everywhere". Changing your own password reissues the cookie for the current browser.
Sign-in
bcryptjs with cost 12. Passwords are 12 characters to 72 bytes (the bcrypt limit), cannot contain the email name or the person's first name, and are checked against a bundled list of common passwords.
Two rate-limit buckets, 10 attempts per 15 minutes per IP and 5 per 15 minutes per email. Both fail closed.
Five failures in a row lock the account for 15 minutes. The counter uses findOneAndUpdate with $inc and returnDocument: 'after', and lockedUntil is set from the returned value.
Unknown email, wrong password, locked and deactivated accounts get the same message and similar timing through fakeVerify().
When mustChangePassword is set, every page redirects to /admin/account/password and every API call except password change and logout answers PASSWORD_CHANGE_REQUIRED.
Authorisation layers
src/proxy.ts matches /admin/:path*, skips /admin/login and /admin/auth/*, and verifies the JWT signature and expiry with jose before letting a request through. It never touches the database and never redirects away from the login page.
getCurrentAdmin(), wrapped in React cache(), verifies the token and loads the admin to confirm status: 'active' and a matching tokenVersion.
requireAdminPage(cap) runs in the workspace layout and again in every page, because layouts do not re-run on client navigation. requireCapability(cap) runs in every route handler. Services also receive the viewer and enforce own-record rules.
An invalid session is sent to /admin/auth/clear, which deletes the cookie and redirects once to the login page. That removes the redirect loop seen in tour-travel-3d.
The login page redirects to /admin only when getCurrentAdmin() succeeds. safeNextPath() blocks open redirects.
Request safety
Every mutation goes through withRoute, which applies assertSameOrigin (Sec-Fetch-Site must be same-origin, with an Origin host check as fallback), JSON content type, a 64 KB body limit, zod parsing and the adminMutation rate limit of 120 per minute per admin, which fails closed.
Responses use one envelope, { ok: true, data } or { ok: false, error: { code, message, fields } }.
Error codes include UNAUTHORIZED, FORBIDDEN, NOT_FOUND, VALIDATION_FAILED, CONFLICT, RATE_LIMITED, PASSWORD_CHANGE_REQUIRED, STEP_UP_REQUIRED, SELF_ACTION, LAST_SUPERADMIN, LINK_MISMATCH, CURRENCY_MISMATCH, FX_RATE_MISSING, PAYMENT_EXCEEDS_DUE, ENTRY_LOCKED and HAS_LINKED_RECORDS.
Mongoose runs with sanitizeFilter and strictQuery on. Every operator we write is wrapped in mongoose.trusted(), and filters are built only from zod-parsed values. audit:filters enforces this in CI.
Client IP comes from getClientIp(), which prefers x-vercel-forwarded-for and otherwise takes the rightmost X-Forwarded-For hop minus TRUSTED_PROXY_HOPS, collapsing IPv6 to /64. IPs are stored only as salted SHA-256 hashes.
Multi-document writes run in a transaction with retry. That covers a payout with its work-order sums, a paid team payout with its work-log locks, enquiry conversion, admin role changes and every audit write.
Data protection
Services return DTOs from src/services/serialize. Password hashes, pay notes, payment notes and IP hashes never leave the server unless the viewer holds the capability for them.
Private media (receipts, attachments) is served only to signed-in admins with the matching money capability. Public media is served from /media/[id]/[filename] with immutable caching. SVG is sanitised on upload and served with Content-Security-Policy: sandbox and nosniff.
/admin and /api/admin send Cache-Control: no-store and X-Robots-Tag: noindex, nofollow. Admin layouts are force-dynamic.
Site-wide headers are CSP with connect-src 'self' https://api.web3forms.com and form-action 'self' https://api.web3forms.com, frame-ancestors 'none', HSTS, nosniff, Referrer-Policy: strict-origin-when-cross-origin and a Permissions-Policy that turns off camera, microphone, geolocation and payment.
audit:boundaries fails the build if a client component imports models, the database, auth or bcrypt, or if anything under src/app/admin reaches three.js or the 3D scene folder.
Enquiry intake with Web3Forms
The contact form fetches a signed form token from /api/form-token (HMAC with FORM_TOKEN_SECRET and the issue time).
On submit the browser sends two requests at once with Promise.allSettled. One goes to https://api.web3forms.com/submit with NEXT_PUBLIC_WEB3FORMS_ACCESS_KEY, which is public by design and restricted to the ProDevly domain in the Web3Forms dashboard. The other goes to /api/leads.
/api/leads checks Content-Length (32 KB cap), same origin, the leadCreate rate limit of 5 per 10 minutes per IP (fails open), the form token (under 3 seconds is a silent discard, over 2 hours asks the visitor to refresh), the honeypot field companyWebsite (silent discard with a decoy 200), zod, spam heuristics and the 10-minute duplicate window. It then saves the lead and an audit entry and answers 201.
The visitor sees success when either request succeeded. When both fail, the form shows the error and the email address from siteInfo.

10. Seed and scripts
Superadmin seed, npm run seed
Loads env with @next/env so .env.local works.
Validates everything before connecting. The script holds the three names, Aman Gupta, Lakshya Sharma and Shivansh Kaushik. Emails and initial passwords come only from SEED_AMAN_EMAIL, SEED_AMAN_PASSWORD, SEED_LAKSHYA_EMAIL, SEED_LAKSHYA_PASSWORD, SEED_SHIVANSH_EMAIL and SEED_SHIVANSH_PASSWORD. Each password must pass the live passwordSchema from src/lib/validation/auth.ts, and the three emails must differ. Any missing or weak value stops the script with a message naming the variable and exit code 1. No email or password is written in code.
Connects with the URI masked in logs. For each person it runs updateOne({ email }, { $setOnInsert: { ... } }, { upsert: true }) with role superadmin, status active, mustChangePassword: true, tokenVersion: 0 and a bcrypt hash at cost 12. An account that already exists keeps its password, role and status. Running the seed again changes nothing.
Creates with $setOnInsert the settings document global, the siteInfo document site with only the display name, and the internal client "ProDevly (internal)".
Writes an audit entry seed.superadmin_created for each account it created, with the actor "seed script".
Prints name, email and created or already present for each person, and a reminder to remove the six SEED_* variables after the first sign-in.
With NODE_ENV=production it also requires --confirm-production.
On first sign-in the guard sends each superadmin to /admin/account/password. Nothing else works until they set a new password, which must differ from the seeded one. The change clears mustChangePassword, increments tokenVersion and reissues the cookie.
Scripts
Command | What it does | 
npm run dev:db | Starts a single-node MongoMemoryReplSet from mongodb-memory-server on port 27018 with replica set rs0 and data in .mongo-data/. A replica set is used so transactions behave as on Atlas. Use MONGODB_URI=mongodb://127.0.0.1:27018/prodevly?replicaSet=rs0. | 
npm run seed | The idempotent superadmin seed above. | 
npm run db:indexes | Imports every model, prints diffIndexes() for each, then runs syncIndexes(). --dry-run only prints. Runs in the deploy pipeline before traffic, because autoIndex is off in production and the TTL and unique indexes depend on it. | 
npm run admin:reset-password -- --email <email> | Break-glass reset for when no superadmin can sign in. Takes the new password from RESET_PASSWORD, sets mustChangePassword, increments tokenVersion, clears the lockout and writes an audit entry. | 
npm run fx:fetch | Pulls ECB reference rates through the Frankfurter API for the enabled currencies into fxRates with source ecb. It never overwrites a manual rate for the same date. /api/cron/fx runs the same code on a daily schedule. | 
npm run reset:rate-limits | Clears rateLimits in development and test. Smoke tests use it so they never spoof forwarding headers. | 
npm run verify | Lint, audit:filters, audit:boundaries, next typegen && tsc --noEmit, then next build. | 
npm run smoke | Black-box HTTP test with a cookie jar against a running dev server and the dev database. | 
Smoke test checks
A signed-out request to /admin redirects once to /admin/login.
After tokenVersion is bumped, a request with the old cookie redirects once through /admin/auth/clear to login.
A seeded superadmin gets PASSWORD_CHANGE_REQUIRED until the password is changed.
A superadmin creates an admin. That admin gets 403 on /api/admin/admins and on payment routes, and gets access to payments after a grant.
Self-deactivation answers SELF_ACTION. Demoting the last active superadmin answers LAST_SUPERADMIN.
A payment naming a task from another project answers LINK_MISMATCH.
A USD payment stores rate and INR. The payments dashboard total equals the sum of inrMinor, and voiding the entry removes it from the total.
A payout against a work order in another currency answers CURRENCY_MISMATCH.
Marking a team payout paid locks the work logs in its period.
The contact form honeypot returns a decoy success and stores nothing. A valid enquiry is stored and appears in /admin/enquiries.
